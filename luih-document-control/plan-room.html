House Document Control

The goal is that everyone, from architecture to the superintendent on site, works from the same current set. This page covers the discovery evidence, as-is and to-be flows for permits and occurrences, a folder standard aligned with BT, a LUIH OS feature concept, the BT and Slack integrations, and the plan for getting the current set to site.

Executive summary

10+field incidents in 4 job channels traced to an outdated or ambiguous document
4–5manual steps per status change: Drive, BT, ClickUp, Slack, then a repost (estimate from interviews)
~35%of messages in job channels are document-update posts (estimated from 4 channels)
0mechanisms that confirm the field actually received a new revision
What we learned
  • The storage model is sound. Drive holds the full history and BT holds only the latest PDFs. Nobody disputes this split.
  • The failures happen after approval, in four places. People aren't told a revision is coming. Revisions aren't batched per house. There's no single versioned "current set". Changes don't propagate to the related sheets, the Design Book or the field.
  • Every status change is retyped by hand into 4 systems. Luiza put it plainly: "It's more about attention than time".
  • The folder template exists, but every house has drifted from it: four date formats, R-numbers reused on different dates, and occurrence folders in three different places.
What I recommend
  • Keep Drive as storage and BT as the field's view. Build LUIH OS as the control layer that owns state: sets, sheets, revisions, packages and acknowledgements. Don't build a new file system.
  • Introduce one Set Version per house (V1, V2, …) that the field can say out loud: "we're on V8". Sheets keep their own R-numbers underneath.
  • Replace the copy-paste loop with one "Publish" action. It moves files in Drive, pushes the latest set to BT, updates ClickUp, posts to Slack and queues a print job.
  • Close the loop on site with an acknowledgement plus a QR code on every printed sheet, so anyone can check whether a sheet is still current.
  • Sequence matters: Phase 0 (naming and folder standard plus governance, no code) captures roughly 30% of the value in 2 weeks.
Challenge to the brief

The brief frames this as a document-management problem ("better than Google Drive"). The evidence says it's a change-control and propagation problem. Oberlin, Mulbry and Stetson didn't fail because a file couldn't be found. They failed because a change wasn't announced, wasn't propagated, or wasn't acknowledged. If we ship a nicer folder browser without the publish → notify → acknowledge loop, we'll repeat those incidents with better UX.

Structural facts we have to design around

  • Exceptions are normal, not edge cases. Construction sometimes builds before the occurrence exists, so the revision is effectively an as-built. Sets get released before the stamp arrives. Revisions get cancelled mid-flow. Not every occurrence goes to the city: some close with an EOR letter instead.
  • "Approved" isn't the same as "issued". The city approves, then the fee is validated and paid, then the permit card arrives, then the stamped plans. Luiza only marks the milestone after both the card and the stamped plans are in.
  • Ownership is concentrated. Ingrid: "I now manage all occurrences." Luiza owns permit submission. Both are single points of failure.
  • The pieces already exist: Ticket Hub (single intake), the D&P Phases 7.3–7.9 in ClickUp (which map 1:1 to folder states), the Specbook versioning in LUIH OS (v1/v2/v3 plus a Slack bot), the Submission Checklist and the Comment Agent, and a sheet-correlation matrix built from Slack (64% of plan revisions are multi-discipline).
  • The "D0" label isn't used anywhere in Drive. Versions are a mix of R00–R04, _v1, dated folders and "Rev 4" stamps from the city.

A-4

Folder standard · Drive mirrors the BT template; BT gets only the latest

Rule: folders 00–04 have the same number and name in Drive and BT. Drive-only folders start at 05, so nobody has to translate between the two systems. BT holds only the current PDFs. Drive also holds the history and the working files. Once Phase 2 is live, people stop moving files by hand; LUIH OS does it.

Naming standard
  • Sheet file: <SHEET>_<HOUSE>_R<nn>_<YYYY-MM-DD>.pdf
  • Package: PKG-<nn>_<YYYY-MM-DD>_<TRIGGER>_<scope>, where TRIGGER is PERMIT, CITY-Cn or OCC-<ClickUp id>
  • Set version: V<n> per house, incremented on every Publish
  • ISO dates only. This removes abr.07, Sept.17, Aug.31.026 and Sep.08.2029 in one rule.

Choice I made, open to challenge: Approved stays flat and current (Amherst style), and the history moves into immutable packages. Mulbry keeps dated approved snapshots instead, which forces the field to work out which snapshot is current. Packages preserve the same history without that ambiguity.

P-1

LUIH OS feature · "Plan Room"

Plan Room is a module per house inside LUIH OS. It follows the principle already in the architecture doc: "Platform owns state, ClickUp owns workflow." Files stay in Drive. LUIH OS owns which file is current, why it changed, and who has seen it.

Why this beats Drive for Ops Better
  • A sheet register, not folders. One row per sheet with its current revision and status. "What's the latest?" becomes a glance instead of a search.
  • Upload once. Drag the PDFs into a package and the system names, files, mirrors and announces them.
  • Linked-sheet prompt. Change C-1 and Plan Room asks: "L-1 and A-2 changed together in 9 of 10 past drainage revisions. Include them?" This uses the matrix built from Slack.
  • Package timeline. A kanban view (Draft → Signing → Ready → At city → Approved → Published) that reads and writes ClickUp D&P phases 7.3–7.9.
  • Visible exceptions. Released-before-stamp, as-built and cancelled are real states with owners and due dates.
  • Audit trail. Who published what, when and why. That ends the silent BT reverts.

P-3

Getting the latest version to site

The constraint is cultural: Mike's world runs on radio, paper and phone. That means paper stays, but paper has to be able to tell you when it's out of date. Options are ranked by leverage relative to effort.

#IdeaHow it worksPillarEffort
1QR code on every printed sheetStamped in the title block at Publish. Scanning shows "✔ Current (V8)" or "✖ Superseded by R05 on Oct 8. Open current". It also goes on the blue bag cover and the job sign, where it opens the current set.BetterLow
2Acknowledge plus escalationSlack button or a BT daily log line: "Plans updated to V8". If nobody acknowledges within 24h, escalate to the construction manager. The acknowledgement rate becomes a KPI per superintendent.BetterLow
3Automatic print with a change cover sheetThe changed sheets and a one-page "what changed" (clouded deltas, reason, trades affected) print in the office. Swap them in the blue bag and return the old ones. A PM without the paper is a visible gap.FasterLow
4Pre-milestone gateThe BT schedule items for framing, MEP rough and trusses require an acknowledgement of the latest Set Version before they can start. This would have caught Mulbry's 9' trusses.CheaperMedium
5Superseded watermarkAny file moved to 99. Superseded gets a red diagonal "SUPERSEDED — see V8" stamp, so forwarded PDFs are self-correcting.BetterLow
6Site tablet showing the current setA ruggedized tablet in the blue bag pinned to the BT current-set view. Only worth it once options 1–3 are adopted.FasterMedium

Recommendation: ship 1, 2 and 3 together in Phase 1. Each one alone is weak: QR without acknowledgement relies on curiosity, and acknowledgement without paper misses the person on site. Together they create a closed loop with an audit trail. Option 4 is the strongest control, but it needs construction leadership to agree to the gate.
